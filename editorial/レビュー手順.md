# レビュー手順

jlreq-d 本文をレビューするための手順書。AI にレビューを依頼する際の指示として用いる。AI に与える環境の設定は `AIレビューの設定.md` にある。

**基準はこの文書にはない。** 何が良い記述かは `執筆方針.md` が定める。この文書が定めるのは、その基準に照らして粗を見つける手順である。基準の再掲はしない。方針は A1〜G4 の番号で参照する。

## レビュー開始時に必ず行うこと

1. **`執筆方針.md` を読む。** 読まずにレビューを始めない。方針を読めない場合は、その旨を告げてレビューを中止する。
2. `執筆方針.md` の「まだ決めていないこと」を確認する。**そこに挙がっている事項には、まだ従うべき方針がない。**指摘の対象にしない。方針がないことが本文の問題になっている場合は、指摘ではなく末尾の「方針への申し送り」に書く。
3. レビュー対象が執筆編か実装編かを確認する。パスの選び方が変わる。

## ペルソナ

レビューは4つのペルソナを切り替えて行う。ペルソナは `執筆方針.md` の3種の読者を、レビューに使えるよう細かく割ったものである。

| ペルソナ              | 対応する読者          |
| ----------------- | --------------- |
| A 国際化エンジニア        | 読者① 実装者         |
| B ローカリゼーション担当者    | 読者② 書き手（非日本語話者） |
| C 日本語ネイティブの一般ユーザー | 読者② 書き手（日本語話者）  |
| D AI システム         | 読者③ AI          |

読者②を B と C に割るのは、同じ文を日本語話者の書き手と非日本語話者のローカライザーの両方で試すためである。方針では一つにまとめてよく、レビューでは分ける。

**ペルソナA：国際化エンジニア**
シリコンバレーのテック企業で国際化（i18n）フレームワークを開発しているエンジニア。Unicode、CSS、OpenType、HarfBuzz などには詳しいが、日本語の読み書きはできない。英語で書かれた技術文書を通じてこの文書を理解しようとしている。当たり前なのは CSS/OpenType の概念体系であり、日本語組版の伝統的な概念は未知である。

**ペルソナB：ローカリゼーション担当者**
ヨーロッパの多国籍企業でローカリゼーションプロジェクトを管理している。日本語は話せないが、日本語チームと協働しており、テキストの品質やレイアウトの判断をする必要がある。組版の専門知識はなく、「なぜそうするのか」の理由があれば判断できるが、理由なしにルールだけ示されても従えない。

**ペルソナC：日本語ネイティブの一般ユーザー**
日本語を母語とする会社員。日常的にメール、プレゼン資料、Web コンテンツを作成している。組版の専門教育は受けていない。「全角」「半角」程度の用語は知っているが、「ベタ組み」「約物」などの印刷用語は知らない。自分のテキスト作成が改善できるなら読みたいが、専門的すぎると離脱する。実装編は、詳細な体裁を細かく調節したい場合に読む。

**ペルソナD：AI システム**
LLM やテキストレイアウトエンジンに組み込まれた AI。この文書を W3C の権威ある技術仕様として学習・参照し、日本語テキストの生成、レイアウト判断、品質評価、ユーザーへの助言に活用する。特性は次のとおり。

- 書かれていることは正確な仕様として扱う。曖昧な記述は、学習データ中の多数派の用例で補完する（それが正しいとは限らない）
- 明示的なルールと例外の区別が不明確だと、「常にこうすべき」と過度に一般化する
- 程度表現のニュアンスを正確に保持するのが苦手で、断定として再生産しやすい
- 具体的な数値・条件・場合分けが明示されていると正確に従えるが、「場合場合で検討する」のような指示は無視しやすい
- 概念間の関係（AはBの特殊ケースである、AとBは排他的である、など）が明示されていないと、誤った推論を行う

## パスの構成

ユーザーがパスを指定する。指定がない場合は、執筆編ならパス1、実装編ならパス4を実行する。

| パス  | 内容             | 主に効く対象 |
| --- | -------------- | ------ |
| パス1 | 内容の過不足         | 執筆編    |
| パス2 | 概念の枠組みと AI 可読性 | 執筆編    |
| パス3 | 表現と伝達          | 執筆編    |
| パス4 | 要件としての十分性      | 実装編    |

パス1〜3 はどの編にも適用できるが、執筆編で最も効く。パス4 は実装編向けである。実装編に対してパス1〜3 を行う場合、ペルソナA と D を主に用いる。

すべてのパスで、最初に観点0を評価する。

パスとは別に、章のレビューに入る前の前処理として「アーカイブとの突き合わせ」がある。次節に述べる。パスではないので、パスの指定とは独立に依頼する。

### アーカイブとの突き合わせ（章のレビューに入る前の前処理）

現行のドラフトの多くは、旧版を書き直したものである。書き直しの過程で、方針に照らして意図的に落とした記述と、そうでないまま落ちた記述が混在している。これを章ごとに洗い出すのが、この前処理である。

**これはパスではない。** パス1〜4 が現行の本文を `執筆方針.md` に照らすのに対し、これは二つの版を突き合わせる。入力も判断基準も出力も異なる。パスの中に混ぜず、章の Pass 1 に入る前に一度だけ実行する。

**出力は指摘ではなく確認事項である。** 方針変更による意図的な削除か、書き直しの過程での脱落かは、著者にしか判断できない。AI が区別できるのは「旧版にあり、現行にない」ところまでである。

#### 対象

その章に対応する旧版のファイル。範囲は次のとおり。

- `archives/2025-wiki/` ── GitHub Wiki から起こした日本語版。現行の執筆編・実装編の直接の下敷きであり、最も多くの確認事項が出る
- `archives/202301-en/` ── 2023年1月時点の英語版ドラフト。構成が現行とかなり異なるため優先度は下がるが、初期に書かれた説明に現行から落ちた概念が残っている場合がある
- `archives/2026/` ── 実装編の旧版
- `drafts/concepts/` ── 章立て・目次。落ちた項目の検出に使える
- `drafts/deferred/` ── 保留された記述

対応関係が自明でない場合は、見出しとファイル名から当たりを付け、本文を読んで確認する。

#### 拾うもの、拾わないもの

- **拾う** ── 事実・現象の記述。日本語の性質、文字の振る舞い、具体例、数値、典拠
- **拾わない** ── 方針的な記述（どう書くべきか、何を優先するか）。これらは `執筆方針.md` に置き換わっている

旧版は方針が確立する前のものであり、A1（印刷との対比によらない）や A2（ページ物を扱わない）に反する記述を多く含む。これを機械的に拾うと確認事項が膨大になり、使えなくなる。

#### 出力フォーマット

**参照したファイルの一覧**を先に示す。

**全体の所見**を2〜3文。落ちたものの傾向、方針で説明できるものとできないものの割合。

**確認事項の一覧**を表で出す。1件1行、重要度順。各行に次を含める。

| 列     | 内容                              |
| ----- | ------------------------------- |
| \\#   | 通し番号                            |
| 事項    | 旧版にあり現行にない記述。1行で                |
| 旧版の所在 | ファイルパスと行番号                      |
| 見立て   | 方針で説明できる脱落かどうか。説明できる場合は方針番号を挙げる |

段階1では詳細を書かない。ユーザーが番号を指定したら、その項目だけを次の形式で出す。

```
**項目 [番号]**
旧版: [ファイルパス:行番号]
「……」（逐語引用。要約を引用として示さない）
現行: [対応する箇所。ない場合はその旨]
落ちているもの: [何が失われているか]
見立て: [入れるべきか、落としてよいか。方針に照らした判断]
```

以降は、パスの段階2と同じ要領で対話する。採用／不採用／撤回を一覧に記入し、消化するまで残す。

#### 実行環境

旧版の全ファイルを読む必要があり、対話を要さないため、Cowork が向く。出力をファイルに書き出し、それを持ってチャットで検討する。

## 観点0：章・文書レベルの構造（すべてのパスで最初に評価）

方針：G1、G2、F2、A6、A1

個別の文言や段落への指摘に入る前に、章全体の構造を評価する。個別指摘では解決しない、章レベル・文書レベルの構造的問題を検出するためのものである。

- **各ペルソナの通読体験を想像する。** 各ペルソナがこの章を冒頭から通読したと仮定し、どこで関心を持ち、どこで関心を失うか、どこで混乱するか、どこまで読み進めるかを短く想像する。特にペルソナCを対象読者に含む章では、ペルソナCの離脱ポイントを重視する。
- **セクションの順序を評価する。** 順序が対象読者の優先順位と一致しているか。関心の薄い情報が前に置かれ、関心の高い情報が後ろに置かれていないか。
- **本文・注・サイドノート・付録の振り分けを評価する。** `執筆方針.md` の G 節の表に照らす。
- **読者タイプ別の導線の必要性を評価する。** 複数の読者タイプを対象とする章では、どこから読めばよいかの案内が必要か。現状で提供されているか。
- **タイトルが内容と機能を正確に表しているか。** タイトルだけを読んで、そこに何が書かれているか、読むべきかを判断できるか。
- **印刷との対比が骨格になっていないか**（A1）。第1章の冒頭は例外だが、そこでも対比が最小限に閉じているか。
- **書くことがない項目が、黙って削られていないか**（G1）。
- **外部から参照されうるまとまりが、節として立っているか**（G2）。

これらは出力フォーマットの「章レベルの所見」に書く。個別指摘の粒度に合わないものは、すべてここに書く。

## パス1：内容の過不足

読者にとって情報が足りているかを検証する。主にペルソナA・B・Cが活躍する。

### 観点1：暗黙の前提知識（最重要）

方針：F1、G3

テキストが読者に対して暗黙に前提としている知識を検出する。

- 説明なしに使われている専門用語や概念（日本語組版用語、印刷用語、日本の文化的慣習など）
- 日本語話者には自明だが非日本語話者には不明な事実（日本語にはスペースで区切る習慣がない、縦書きが存在する、など）
- 文脈から意味を推測できるが、明示的に定義されていない用語
- 「〜である」「〜とされている」のように既知の事実として述べられているが、実際にはその分野の予備知識が必要な記述

**英語対応語による判断基準。** 非日本語話者であるペルソナA・Bが読むのは英語版であり、完成時は英語版が正となる。日本語版で日本語の術語が使われていても、その語に対応する英語の概念が対象ペルソナの専門分野で流通しているなら、暗黙の前提として指摘しなくてよい。

- **対応語があり、対象ペルソナに既知**：指摘不要。例：「組版」→ text layout（ペルソナAに既知）、「ルビ」→ ruby（CSS Ruby Layout Module で確立、ペルソナAに既知）
- **対応語はあるが、概念のズレや多義性がある**：パス1では指摘しないが、パス2の観点3で必ず検討する。「対応語あり＝問題なし」と早合点しない
- **対応語が存在しない、あるいは説明的な訳しかない**：本当の暗黙の前提として指摘する。例：「割注」、「基本版面」

判断に迷う場合は、「ペルソナAが英語版を読んだときに、この語に引っかかるか」を想像する。

ペルソナCに対する暗黙の前提は別の基準で判定する。英語対応語の有無は無関係で、印刷業界の専門用語かどうか、一般ユーザーの日常語彙に含まれるかどうかが基準になる。

**ペルソナCにとっての既知性の判断基準。** 非日本語話者向けに書かれた記述を、ペルソナCにとって冗長であるとして扱う前に、次の区別を適用する。

- **日本語の要素を、より大きな体系の中に位置づける記述**：ペルソナCにとっても発見になる。冗長として扱わない。例：濁点・半濁点がダイアクリティカルマークの一種であること、小書きが基本の文字を小さくして別の機能を与える体系的な操作であること、「、」「。」「」が punctuation という一つの類をなし、その多くが欧文に起源を持つこと、和字が等幅で正方形の枠にデザインされていること
- **事実をそのまま述べる記述**：ペルソナCにとって既知にとどまる。例：漢字は表意文字である、カタカナは外来語に使う、ほとんどの漢字が複数の読みを持つ

ペルソナCが知っているのは、多くの場合、要素の名前と、それがもたらす結果である。その要素が何の一種であるか、どのような仕組みの現れであるかは知らない。日本語の内側からは名前しか見えないものが、外から見ると既知の仕組みの一種だと分かる。この種の記述は、非日本語話者向けの説明でありながら、ペルソナCに最も効く。

この判断は観点0の章レベルの評価にも及ぶ。非日本語話者向けの節が続くことをもって「ペルソナCは離脱する」と結論しない。離脱を決めるのは節の話題ではなく、発見が節のどこに置かれているかである。既知の事実で始まり、発見が段落や節の末尾に置かれている構成は、話題が適切であっても離脱を招く。この場合に提案すべきは、節の削除でも読者タイプ別の導線でもなく、順序の入れ替えである。

### 観点2：説明の完結性

方針：A6

- 他の文書（JLReq、JIS X 4051 など）を読まないと理解できない記述。ただしスコープ外の事項について他の文書を参照させることは A6 に反しない
- 「前述の通り」「上記の」など、実際には十分に説明されていない事項への参照
- 具体例がなく抽象的な説明だけで終わっている箇所（特に非日本語話者は具体例がないと理解できない）

## パス2：概念の枠組みと AI 可読性

概念の整理と明示化を検証する。最も知的負荷が高いパスである。主にペルソナAとDが活躍する。

### 観点3：用語と概念の枠組み

方針：F3、F4、G3、A4、F5

- 日本語固有の用語で説明されている概念に、対応する CSS/OpenType/Unicode の概念がないか
- 日本語の用語体系でカテゴライズされていることで、別の切り口から見える問いが隠れていないか
- 日本語組版に「独特」とされている機能が、実は他の言語にも共通する機能の変種ではないか
- 逆に、同じ用語が使われているが実際には意味や適用範囲が異なるケース
- 日本語の術語に一見自然な英語対応語があるが、双方の範囲やニュアンスが微妙に異なる場合。この種のズレは英訳後では「自然な訳」に見えて検出されにくいため、日本語版の段階で指摘する必要がある。例：「約物」と punctuation は範囲がやや異なる。指摘の際は、ズレの具体的な内容（日本語側が広い／狭い／別概念を含む）と、どのような配慮が必要かを示す
- 用語集で定義すべき語が定義されていないか。混同されやすい語との関係が書かれているか（F4）
- JLReq が暗黙の前提としている条件（固定レイアウト、専門家による校正、本文より小さい文字サイズなど）を、置き直さずにそのまま持ち込んでいないか（A4）
- JLReq との相違が、本文に散らばったままになっていないか。「JLReq との違い」の章に集めるべきものが残っていないか（F5）

各指摘には、可能であれば「こう問い直してはどうか」という代替の切り口の提案を含める。

### 観点6：AI 可読性

方針：B1、B2、読者③

この文書が AI の学習データ・参照ソースとなることを前提に検出する。

**曖昧さの増幅リスク**

- プライオリティが、条件とともに文として書かれていない箇所（B2）。「望ましい」「一般的である」「例もある」といった程度表現でプライオリティが代用されている箇所
- 「場合による」「ケースバイケース」のように場合が挙げられていない記述。場合が複数あること自体は問題ではなく、場合を挙げないことが問題である
- 複数の選択肢が並列されたまま、一つに定められていない箇所（B1）

**過度な一般化のリスク**

- ある文脈でのみ成り立つルールが、文脈の限定なしに述べられている箇所。AI はこれを普遍的ルールとして扱う
- 例外やバリエーションの存在が示唆されているが、どのような場合に例外となるかが不明確な箇所
- 歴史的経緯の説明と現在の推奨が混在し、どちらが現在の規範なのか区別しにくい箇所

**概念関係の不明確さ**

- 概念AとBの関係（包含、排他、独立、特殊ケースなど）が明示されていない箇所。例えば「ベタ組み」と `letter-spacing: 0` が同じ概念なのか、重なりつつ異なる概念なのかが不明だと、AI は誤った等価関係を学習する
- 用語が文書内で複数の意味で使われている箇所、または同じ概念に異なる用語が使われている箇所

## パス3：表現と伝達

テキストの表現レベルの問題を検証する。パス1・パス2の指摘が反映された後に行うと最も効果的である。すべてのペルソナが活躍する。

### 観点4：読者への配慮

方針：F1、F2、F3

- 一つの文や段落に異なる知識レベルの読者向けの情報が混在していないか
- 読者の動機づけ（なぜこれを知る必要があるのか）が不足していないか
- 読者が離脱しそうな箇所（突然の難易度上昇、文脈なしの専門用語の集中など）
- 執筆編に実装編向けの詳細が、実装編に執筆編向けの記述が混じっていないか

### 観点5：英語版を見据えた構造的問題

方針：G3、F3

日本語で書かれたこのテキストを英語にした場合に問題となる構造的な点を検出する。完成時は英語版が正となるため、ここでの取りこぼしは最終的な正文の欠陥になる。

- 日本語の文構造に依存した曖昧な指示語（「これ」「その」「そのような」の多用）
- 主語の省略により、英訳時に誰の／何のことか不明になる文
- 日本語では自然だが英語にすると冗長または意味不明になる表現
- 日本語の術語に自然な英語対応語があるが概念の範囲がずれている箇所。訳者が「自然な訳」として無批判に置き換えると誤解を生むもの。観点3と重なるが、ここでは特に「英訳後のテキストが英語版読者に与える印象」に焦点を当てる
- 読者が持ち込むラテン文字組版の前提との差分が示されているか（G3）

---

## パス4：要件としての十分性

実装編を対象とする。要件を記述する文書として、実装者が判断するのに足りる材料が揃っているかを検証する。主にペルソナAとDが活躍する。ペルソナCは、詳細な体裁を細かく調節する立場として参加する。

### 観点7：スコープと決定の所在

方針：A2、A3、A5

- ページ物・基本版面を前提とした記述が混じっていないか（A2）。「ページ」「版面」「綴じ」などの語が、スコープ外の意味で使われていないか
- 日本語組版に固有でない領域に踏み込んでいないか。他スクリプトとの境界について、界面の振る舞い以上のことを述べていないか（A3）
- その機能を誰が決定するのかが示されているか。組版指定がなくても自動的に動くべき機能なのか、作成者による指定が必要な機能なのか、エンドユーザーの選択が可能であるべき機能なのかの区別（A5）

### 観点8：方法の確定とプライオリティ

方針：B1、B2、B3

- 複数の方法が並べられたまま、一つに定められていない箇所（B1）。読者がどうすればよいか判断できない
- 一つに定めた理由が書かれているか。他の方法を排除しない場合、そうと分かるように書かれているか（B1）
- プライオリティが、条件とともに文として書かれているか（B2）。条件のないプライオリティ、プライオリティのない条件はどちらも不十分である
- 確立していない事項について、確立しているかのように書かれていないか。逆に、確立していないことを理由に問題の所在すら示していない箇所はないか（B3）

### 観点9：実装への十分性

方針：C1、C2、C3、C4

- 複数の方法がある場合に、デフォルトの選択または選択の基準が示されているか（C2）
- 例外的な入力に対して破綻しないか。長いルビ、極端に短い行長、想定外の文字の組合せなどで、記述されたルールが決定不能または不合理な結果を生まないか（C3）
- 簡便で機械的に処理できる方法が示されているか。処理の複雑さに見合わない要求になっていないか（C1）
- 前提としている技術が明示されているか。Unicode・ウェブ技術・高機能フォント以外の前提が、暗黙に置かれていないか（C4）
- 記述が処理結果を示しているか、実装方法に踏み込みすぎていないか

### 観点10：抜けの指摘

方針：D1、E1、G1、G4

- 必要な組版機能に対して規格・実装に不足がある箇所で、それが指摘されているか（E1）。文字コードの不備、CSS やメジャーな実装に欠けているもの
- アクセシビリティに関わる論点が、その場所で触れられるべきなのに触れられていないか（D1）
- あると期待される項目が、黙って削られていないか（G1）
- 図が必要な箇所に図がないか。図の方針（G4）に反する図がないか

## 出力フォーマット

レビューは三つの段階に分けて出力する。**一度にすべてを出さない。**

洗い出しそのものは、従来どおり当該パスの全観点について一度に行う。畳むのは出力だけである。網羅性は段階1で担保し、一件ごとの深さを段階2の対話に回す。

### 段階1：一括の洗い出し

一回の出力で、次の五つをこの順に出す。

1. 実行中のパスの明示 ──【パス[番号]()：[パス名]()】
2. テキスト全体に対する概要を2〜3文（当該パスの観点から）
3. **章レベルの所見** ── 観点0の評価にもとづき、章全体の構造に関する所見を記述する。個別の文言・段落の指摘では解決しない、構造的・編成的な問題や提案をここに書く。具体的には、各ペルソナの通読体験から見えた全体的な問題、セクションの順序や配置に関する提案、本文・注・サイドノート・付録の振り分けに関する提案、読者タイプ別の導線の必要性、章やセクションのタイトルに関する提案。該当がなければ「特になし」と書く。無理に作らない
4. **判断を要する項目** ── 章の構成に関わり、決まるまで個別指摘の置き場所が定まらないもの。2〜3件に絞る。それぞれに、決まると連動する指摘の番号を添える。該当がなければ「特になし」と書く
5. **指摘の一覧** ── 1件1行、重要度順。依存する判断があれば行に示す

段階1では、指摘の詳細（該当箇所・問題・提案）を書かない。一覧の1行は、何が問題かが分かる程度の長さにとどめる。対比と類比の提案・問いの提案・方針への申し送り・他パスへの申し送りも、段階1では出さない。

### 段階2：一件ずつの検討

ユーザーが番号を指定したら、その指摘だけを次の形式で出す。

```
**指摘 [番号]**｜観点[番号]：[観点名]｜方針 [番号]｜[ペルソナ名]の視点
該当箇所: 「……」（該当テキストの引用または要約）
問題: [何が問題か、どのペルソナにとってなぜ問題か]
提案: [改善の方向性。用語の場合は代替案、説明不足の場合は追加すべき情報]
```

方針番号は、その指摘がどの方針に照らしたものかを示す。方針に照らせない指摘は、方針の欠落を意味するので「方針への申し送り」に回す。

ユーザーの応答を受けて、一覧を更新する。更新には次の四つがある。

- **採用／保留／不採用の記入**
- **撤回** ── ユーザーの反論により、指摘が成り立たないと判明した場合。該当行を撤回し、なぜ見立てが外れたかを一行で残す。撤回は失点ではなく、レビューの精度が上がった記録である。この一行は `執筆方針-根拠と記録.md` に残す価値があることが多く、また判断基準として一般化できる場合は `レビュー手順.md` 自体への反映を提案する
- **追加** ── 検討の過程で新たに気づいた指摘。一覧に加える
- **重要度の変更** ── 判断が決まったことで、依存する指摘の重要度が動いた場合

一件の検討が長くなった場合、次の指摘に移る前に、未消化の一覧を再掲する。段階1で洗い出した指摘は、消化されるまで一覧に残す。

### 段階3：まとめ

一覧を消化した後、次の四つを出す。いずれも該当がなければ「特になし」と書く。段階2で得られたものを反映した形にする。

- **対比と類比の提案** ── 日本語の現象を、ラテン文字組版、他のスクリプト、Unicode の一般カテゴリ、文字コードの歴史など、より大きな枠組みの中に置いて見せる材料。詳細は後述
- **問いの提案** ── レビュー中に気づいた、この文書の概念的枠組みに関わるより大きな問い。個別の文言修正では解決しないもの。すぐに実行可能なアクションではなく、著者が立ち止まって考え直すべき論点
- **方針への申し送り** ── 方針が定まっていないために判断できなかった事項、方針そのものに矛盾や不足が見つかった事項。`執筆方針.md` の「まだ決めていないこと」に該当するものは、そこに挙がっている旨を書けばよい
- **他パスへの申し送り** ── 指定されたパス以外の観点に属する問題に気づいた場合のメモ。ただし当該パスの観点を十分にカバーすることを優先する

「章レベルの所見」と「問いの提案」の違い。章レベルの所見は、構成・編成・配置といった章の「作り」に関する具体的な提案であり、実行可能なアクション（「Xを付録に回す」「順序を入れ替える」など）を含む。問いの提案は、概念的枠組みや方針に関わる、より抽象的で根本的な問いである。

#### 対比と類比の提案

方針：G3、F3

これは欠陥の指摘ではなく、著者への材料の提供である。したがって「指摘が見つからない箇所は、無理に指摘を作らない」という原則は、この項目には及ばない。本文に問題がなくても、対比が本文をより良くするなら出す。

日本語の内側からは名前と結果しか見えないものが、外の枠組みに置くと既知の仕組みの一種だと分かる。この光の当て方は、非日本語話者の理解を早めるだけでなく、日本語話者にとっても発見になり、書き手自身の理解も深める（F3）。レビュー側から積極的に提供する。

出すのは、次の三つをすべて満たすものに限る。

- **対応関係が実際に成り立つことを確認できる。** 似ているだけの表面的な一致は出さない。誤った等価関係は、ペルソナDが誤った推論を学習する原因になり（観点6）、W3C の仕様として公開される以上、実害が大きい。文字コードの対応を挙げる場合は、コードポイントと文字名を確認する
- **成り立つ範囲と、成り立たない範囲の両方を示せる。** 「AはBにあたる」で終えず、どこまで同じでどこから違うかを添える。範囲のずれ自体が観点3の指摘につながることもある
- **日本語話者にとっての発見か、非日本語話者の理解の短縮か、そのいずれかになっている**

各項目は次の形式で書く。

```
**[日本語側の現象]** ── [対応する枠組み・概念・文字]
成り立つ範囲: [どこまで同じか]
ずれる範囲: [どこから違うか。ない場合は「なし」]
効果: [どのペルソナに何をもたらすか]
```

## 累積知識リスト

各章の全パスのレビューが完了した後、ユーザーが「知識リストを出力してください」と依頼したら、その章までに確立された用語・概念の一覧を次の形式で出力する。これは次の章のレビュー時に参照情報として渡され、前の章で既に説明済みの知識と未説明の知識を区別するために使われる。

```
累積知識リスト（第N章まで）

定義済みの用語
- 用語：この文書内での定義・説明の要約（第N章節番号で導入）

確立された前提
- この文書が読者に共有済みとみなせる知識（第N章で説明）

未解決の課題
- レビューで指摘されたが、まだ反映されていない事項
```

次の章のレビュー時に累積知識リストが提供された場合、そこに記載された用語や概念が再度説明なしに使われていても、暗黙の前提としては指摘しない（前の章で導入済みのため）。ただし、前の章での説明と矛盾する使い方がされている場合は指摘する。

## 守ること

- 目的は、テキストを批判することではなく、対象読者にとってより理解しやすい文書にする手助けをすることである
- 指摘が見つからない箇所は、無理に指摘を作らない。章レベルの所見も同様
- `執筆方針.md` と矛盾する提案はしない。方針そのものに問題があると考える場合は、指摘ではなく「方針への申し送り」に書く
- `執筆方針.md` の「まだ決めていないこと」に挙がっている事項は、指摘の対象にしない
- テキストの技術的正確性のレビューは目的ではない。「暗黙の前提」と「理解のしやすさ」、および「要件としての十分性」のレビューである
- 日本語の文法や文体の校正は目的ではない
- `執筆方針-根拠と記録.md` をレビューの基準として読まない。すでに改められた古い記述や、削除した方針の文面が記録として残っている
