# 執筆方針

jlreq-d 本文をレビューする際の基準。**レビューはこの文書に書かれていることのみを基準とする。**

方針は目的ごとのグループ（A〜G）＋番号で参照する。〔Q…〕は末尾の「まだ決めていないこと」へのポインタで、そこに挙がっている事項には、まだ従うべき方針がない。番号はまだ固定していない。

レビューの手順は `レビュー手順.md` にある。各方針の根拠（コーパスからの逐語引用）、決定の記録、他文書への反映事項、プロセスの運用は `執筆方針-根拠と記録.md` にある。**そちらには、すでに改められた古い記述や、削除した方針の文面も記録として残っている。レビューの基準として読まないこと。**

- 完成後は `repo/editorial/` に移す。それまでは `policy/` に置く。
- jlreq-d 本文は完成時に英語版が正となる。この文書自体の英語版は作らない。
- 公開向けの説明は `repo/explainer.md` が担う。この文書はそれを置き換えない。

## A　デジタルの組版を正面から記述する（目的1）

**A1　印刷との対比ではなく、デジタルを正面に据えて書く。**
金属活字・写真植字・JLReq との対比によらない書き方で記述する。理由の理解に有用な歴史的背景は、背景情報として説明する。歴史そのものが目的ではない。第1章の冒頭は例外として対比から入るが、そこでも対比は最小限に閉じ、以降はデジタルを正面から記述する。

**A2　ページ物は扱わない。可変行長のデジタルテキストを中心に据える。**
基本版面をテンプレートとしてページに分割する方法と、冊子形態は扱わない。印刷書籍の見掛けの再現を目的とする電子書籍も扱わない。中心に据えるのは、デジタルデバイス上で表示環境やユーザーのニーズに合わせた柔軟な表示が可能なテキストであるが、UI テキストのようにスクロールを伴わないものも対象に含む。段組は扱う。

**A3　日本語組版に固有でない領域には踏み込まず、界面の振る舞いのみを定義する。**
欧文、数式、添字、単位記号などには踏み込まない。他言語・他スクリプトとの境界については、その界面の振る舞いのみを定義する。

**A4　JLReq が暗黙の前提としている条件を、置き直したうえで記述する。**
JLReq は固定レイアウト、専門家による校正、本文より小さい文字サイズなどを暗黙の前提としている。jlreq-d ではその前提が異なることを明示したうえで記述する。

**A5　誰が決定する機能かを意識して記述する。**
組版指定がなくても自動的に動くべき機能、作成者による指定が必要な機能、エンドユーザーの選択が可能であるべき機能を区別する。印刷ではこれらをすべて組版者が決めて固定していた。

**A6　jlreq-d だけを読んで理解できるようにする。**
組版の記述は jlreq-d で完結させる。スコープ外の事項について他の文書を参照させることは、これと矛盾しない。

**A7　横組を前提として記述し、縦組はまとめて扱う。**
各章の記述は横組を前提とする。縦組については、横組と異なる点をまとめて扱う場所を設ける。両方を並べて書くと、読者は常にどちらの話かを判断しながら読むことになり、適切な行長の範囲のように値そのものが異なる事項では記述が二重になる。横組を前提とすること、および縦組を扱う場所の所在は、各章で一度示す。縦組の優先度が低いという意味ではなく、記述の場所の取り決めである。執筆編・実装編のそれぞれに置く〔Q6〕。

## B　理由と背景を示す（目的2）

「実装を助ける」ことと「将来のために固定しない」ことは、方法を曖昧に書くことでは両立しない。曖昧さは実装者を助けないからである。両立させるのは、方法を一つに定めたうえでその理由を書くこと（B1）と、プライオリティを明示すること（B2）の二つである。

**B1　一つの方法を具体的に定め、その理由を書く。**
複数の案を並べると、読者はどうすればよいか分からない。この機能はこのように行う、この方法を標準とする、と具体的に書き、曖昧にしない。そのうえで、なぜその方法かを示す。理由があることで、読者は事情に応じて別の方法を選ぶ判断ができ、議論と将来の進化が可能になる。他の方法を排除しない場合は、そうと分かるように理由を書く。理由なしに「この方法しかない」とは見せない。各規則の必要性を非日本語話者に対して合理的に説明できることが要件である。

示すのは最適な結果とその理由であって、それを達成する実装方法まで示す必要はない。

**B2　プライオリティを、条件とともに文として書く。**
ラベルを付けるのではなく、文で書く。「不特定多数に向けたテキストでは必須である」「この方法を標準とする。より高い品質を求める場合には〜という方法がある」。ラベルだけでは、どのような場合にそうなのかが伝わらない。ルビは書き手自身のためのテキストには要らないが、不特定多数に向けたテキストでは必須に近い。

条件は、その機能をなぜ行うのかという理由（B1）から導かれる。「〜の場合は必須、〜の場合は不要」と場合を挙げて書くのであって、「場合による」で済ませない。禁じられるのは場合を挙げないことであって、場合が複数あること自体ではない。

「望ましい」「一般的である」「例もある」といった曖昧な程度表現で、プライオリティを代用しない。

どこまで実装するかは、アプリケーションの目的によって決まる。その目的は、そこで書かれるテキストが誰に読まれるかを反映する。JLReq を実装に落とす際の障害の一つが、機能のプライオリティが明らかでないこと、複数の方法があるときの選択基準がないことだった。

**B3　確立していない事項は、問題の所在を示すにとどめる。**
確立された方法がないものは、どんな問題があるかを主に示し、いくつかの方法を挙げる。実装依存であること、今後の課題であることを明記する。

## C　実装コストを下げる（目的3）

**C1　シンプル化する。**
ある程度の品質を確保しながら、例外が少なく機械的に処理できる方法をまず示す。理想でなくとも実用に足りることを優先する。処理が複雑になることを理由に採用しないという選択もありうる。ただし、単純な水準にとどまることが目的ではない。より洗練された方法も紹介し、品質を高める道筋を示す。

**C2　デフォルトを示す。**
複数の方法がある場合は、可能な限りデフォルトの選択を示すか、選択のための基準を示す（例：行長に対する最適な行間、禁則の選び方）。JLReq／JIS X 4051 で複数の方法が示されているものも、何を選べばよいか・何が重要かを考慮して絞る。原則として JIS X 4051 の規定によるが、処理系定義として採用できるオプションを採ることがある。

**C3　組版が完全に自動で決まることを前提にする。**
人による判断が介在しない。長いルビなど例外的な入力に対しても、破綻せず合理的な組版を決定できる必要がある。

**C4　前提とする技術を明示し、それを受け入れて記述する。**
現時点の想定は Unicode、ウェブ技術、高機能フォント。前提として採用した技術はドキュメントする。ただし現行の CSS などの制約には縛られない。

**C5　既存の国際的な実装で同じ目的が達成できる場合、日本語固有の方法を要求する実質的な利点があるかを検討する。**
例えば注の表示方法として脚注が既に広く実装されている場合に、割注の実装を同等の優先度で要求することは、実装コストに見合う利点があるかどうかを検討したうえで判断する。日本語の伝統的な方法を記録し紹介することと、それを要件として要求することは区別する。

## D　アクセシビリティ（目的4）

**D1　折々に織り込む。**
アクセシビリティを、誰もが理解しているべき通常のこととして扱う。独立した章も設ける。扱う範囲は A3 による。

## E　規格・実装の不足を指摘する（目的5）

**E1　不足を明示的に書く。**
必要な組版機能に対して規格・実装に不足があれば、洗い出して指摘する。文字コードの不備、および重要であるのに CSS やメジャーな実装に欠けているものを含む。この部分は規格や実装の進みに合わせて頻繁な更新が必要になる。方針としての独立した記述はコーパスになく、目的の記述がそのまま方針として働いている。

## F　読者に届ける（対象読者）

完成時は英語版が正となる。日本語版はその翻訳という関係になる。

**F1　暗黙の前提を作らず、平易に簡潔に書く。**
日本語の知識のほとんどないエンジニアでも理解できるよう、必要な基礎からカバーする。日本語話者には自明でも非日本語話者には不明な事実、説明なしに使われる専門用語、文脈から推測はできるが定義されていない語を残さない。ラテン文字組版との違いという切り口が有効。執筆編ではできるだけ専門用語を避け、中学生なら理解できる程度の平易な言葉で書く。教科書でも学術書でもないので簡潔に。詳細は専門書に譲る。

**F2　執筆編と実装編で読者を切り分ける。**
執筆編は書き手・ユーザー向け、実装編は実装者向け。書き手は執筆編までで読み止めても足りるようにする。実装編も実装方法の解説ではなく要件の記述であり、ソフトウェアエンジニアリングの専門知識を要する箇所はほとんどないので、エンジニアでなくても読める。日本語テキストの詳細な体裁やデザインを扱う人も、実装編の読者として想定する。

**F3　想定読者にとって国際的に認知されている用語を優先する。ただし場合場合で検討する。**
何が「国際的に認知されている」かは編ごとに異なる。実装編では CSS・OpenType・Unicode などで確立している概念・用語がそれにあたる。利点は、伝統的な印刷用語を知らないエンジニアの理解のバリアを減らせること、デジタル組版の文脈で理解しやすい概念であること、共通の用語を使うことで書き手自身がその現象をより深く理解できること、カーニングのように日本語でも使われるようになった語との整合が取れること。

**F4　想定読者の常識では分からない用語は定義する。用語集を作る。**
判断の基準は、その編の想定読者にとって既知かどうかである。用語集の各項目には、定義に加えて、混同されやすい語とその関係を書く。定義だけでは、ある語が別の語の特殊ケースなのか、排他なのか、重なるのかが伝わらない。

日本語と英語で範囲がずれる語は、**英語に合わせる**。そのうえで用語集で説明する。英語版が正であるため、既存の日本語組版用語を英語の概念に安易に当てない。確定しているもの：

| 英語         | 日本語                     |
| ---------- | ----------------------- |
| full-width | 全幅（字詰め方向の幅は、すべてこの語を用いる） |
| ruby       | ルビ                      |

**F5　JLReq からの読者のために、違いを記述する章を設ける。**
jlreq-d で使用しなかった JLReq 用語を説明する。使用しない用語も「JLReq ではこう呼ぶ」と注で紹介する。JLReq との細かな相違（約物の字幅の扱いなど）もこの章に集める。

## G　文書の作り

### jlreq-d に固有のもの

**G1　書くことがない項目も、項目を残して「ない」と書く。**
項目がないと、読者にはなぜないのかが分からない。ある機能が日本語で使われないこと自体が情報になる。

**G2　外部文書からのリンク先となることを考慮する。**
W3C の Script Resources page（Language enablement index）の各項目からリンクできるようにセクションを設ける。外部から参照される以上、章立てとラベル（アンカー）の安定性が重要になる。G1 はこれと表裏で、項目を残すことがリンク先を保つことにもなる。

**G3　読者が持ち込むラテン文字組版の知識を、助けとして使う。**
読者の多くはラテン文字組版の知識を持って読む。その知識が助けになる場合と、誤って持ち越される場合の両方がある。助けになる場合は積極的に使い、誤って持ち越される場合は差分を明示する。

- 英語（ラテン文字組版）に対応する例を添える。英語に似た例があると理解が早い。
- 日本語に固有と見える要素が、既知の仕組みの一種である場合は、そう位置づけて書く。濁点・半濁点はダイアクリティカルマークの一種であり、小書きは基本の文字を小さくして別の機能を与える操作であり、和文約物の多くは欧文に起源を持つ。この書き方は非日本語話者の理解を早めるだけでなく、日本語話者にとっても発見になる。日本語話者が知っているのは要素の名前とそれがもたらす結果であって、それが何の一種であるかではないためである。
- 推奨値が英語や現在の一般的な値と異なる場合は、異なることが明確にわかるように書く（例：行間）。黙っていると、読者は既定の値をそのまま持ち越す。

**G4　図版。**

- 図の中に説明の文字を入れない。
- 図の内容はキャプションと代替テキストで言語化する。
- 例示する文字列はフォントを埋め込む。

〔Q4〕

### 一般に良いとされる書き方

以下は文書一般について言えることで、jlreq-d に固有のものではない。個別の番号は付さない。

章の冒頭に、その章が何を扱い何を扱わないか、どの立場で扱うかを書く。章冒頭の記述は、将来この文書を更新する人へのガイドも兼ねる。同じ話題が複数の章に関わる場合は、どこで何を説明するかを明示して相互参照する。本文・注・サイドノート・付録は下表で振り分ける。例と図は豊富に使うが、例が多すぎると読者が離脱するので、数例を残して他は注に移す。慣用・慣習に言及するときは典拠を示す〔Q5〕。表や図で使う記号は、表・図の前に定義する。記述の粒度はその場所にふさわしいものにし、導入部ではエッセンスだけを述べて詳細は後の節に送る。節や段落は、そこで最も新しいことから書き始め、既知の事実はその説明として後ろに置く。既知の事実で始めると、読者はその節が自分に向けたものではないと判断して読むのをやめる。

数字は、「公用文作成の考え方」（令和4年 文化審議会建議）Ⅰ－４に従う。横書きでは算用数字を用い、四桁以上は三桁ごとにコンマで区切る。兆・億・万は漢字を用いるが、千・百は用いず「5,000」「300」と書く。語を構成する数（三日坊主、一つ、二つ）は漢数字を用いる。

|            | 基準                                                        |
| ---------- | --------------------------------------------------------- |
| **本文**     | その章の読者が、その章を理解するために読む必要があるもの                              |
| **注**      | 本文の主張の根拠、例外、限定、JLReq や他規格との対応。読み飛ばしても本文の理解は成立する           |
| **サイドノート** | 本文の理解には不要だが、理解を助ける補足。他言語との比較、歴史的経緯、関連技術の紹介。「ところで」で始められるもの |
| **付録**     | 通読せず、参照して使うもの。文字クラスの表、詳細な処理例、一覧                           |

### 原稿の記法

ドラフト上の取り決めであり、方針ではない。個別の番号は付さない。

| 記法         | 用途                                      |
| ---------- | --------------------------------------- |
| 〓          | 未確定の参照先。図番号、節番号、典拠〔Q4〕〔Q5〕              |
| `>` 引用ブロック | 著者メモ。本文ではない                             |
| 〈　〉        | 翻訳者への注記。英語の対応語の指示など。日本語版・英語版のいずれにも出力しない |

注とサイドノートの記法は決めていない〔Q7〕。

## まだ決めていないこと

方針の末尾の〔Q…〕はここを指す。ここに挙がっている事項には、まだ従うべき方針がない。**番号は以後固定する。解決した項目の番号は詰めず、欠番として残す。**

（Q1 プライオリティの表記、Q2 本文・注・サイドノート・付録の使い分け、Q3 相対量の示し方は解決した。それぞれ B2、G 節の表、付録3 に反映した。）

**Q4　図番号と参照の書式。**
G4 で図版の方針は定めたが、図に付ける番号と、本文からの参照の書式は決めていない。章ごとの通し番号とするか文書通しとするか。現状のドラフトは未確定の参照先を「〓」で示している。

**Q5　参考文献・出典の書式。**
`repo/drafts/この文書の目的・対象読者.md:88` に実例はあるが、書式の統一規則と外部 URL の扱いを定めた記述がない。

**Q6　縦組をまとめる場所の粒度。**
A7 で、縦組を横組と分けてまとめて扱うことは定めたが、それを独立した章とするか、各章の末尾に置く節とするかは決めていない。実装編には独立ファイル（`実装編_縦組の配置.md`）があり、執筆編には第3章 3.5 として節がある。現状は編ごとに異なる。

**Q7　注とサイドノートの記法。**
G 節の表は本文・注・サイドノート・付録を区別しているが、ドラフト上でこれらを書き分ける記法を定めていない。現状は見出しレベルやインデントが混在している。
